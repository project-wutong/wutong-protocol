## 摘要

Wutong Protocol（以下简称 WTP）是一套自主定义、面向**本地优先原生内容、知识对象、Agent 原生身份及贡献、权限化协作、开放联邦和知识服务化**的可扩展协议。WTP 不要求接入 Wutong 官方网络，也不从属于 ActivityPub、AT Protocol、Matrix、MCP、A2A、Ceramic、AnySync 或某一种 CRDT 实现。其他协议通过能力声明、适配器与有来源的外部资源映射衔接。

**用户可以只使用 Wutong Writer、Knowledge、Publisher 编辑普通原生文件，完全不安装、不启动、不登录 Network/Server，不建立密钥，不使用任何外部服务或 AI。** WTP 核心知识功能在本地库中运行；同步、联邦和执行型 Agent 是明确可选的能力。

本次发布候选工程包包括 **15 种交换类型的 JSON Schema、严格 JSON/签名测试实现、Python/Node 交叉检验、Agent 权限状态机、磁盘与 SQLite 写入意图恢复 PoC、原 v0.1 C++23 Core、自动化测试、参考资料与发布阻断清单**。下面精确定义语法、语义、安全边界及尚未完成的部分。

## 0. 规范术语、状态与解释原则

- 本规范中的 **MUST、MUST NOT、SHOULD、SHOULD NOT、MAY** 仅在大写时按照 RFC 2119 与 RFC 8174 解释。
- **Specification Candidate** 表示结构可以接受第三方审阅与试实现；**Production-ready** 必须另行经过互操作、安全、跨平台与故障测试。`rc.1` **不是**协议稳定或生产可用的保证。
- **原生源文件**：如 `.md`、`.adoc`、`.rst`、`.tex`、`.typ`、`.org`、XML、音视频媒体或自定义格式。没有经过用户授权的转码、改写或编码规范化，都不能当作原文件保存。
- **Object**：稳定可变身份。**Revision**：对象的一个不可变版本记录。**Content Digest**：原始字节的精确哈希。三者不可互换。
- **Principal**：独立的操作主体，含 Human、Organization、Agent、Service；Device 主要表示认证设备。不意味着自然人实名或信任评级。
- **Space**：身份、权限、复制与知识关系的逻辑边界，不必须是文件夹。
- **Agent-native**：Agent 可以是 Principal，拥有受控 Space、接受 Task、提交 Proposal/Artifact、引用并关联 Object；Agent 的声明不能取代身份验证、资源策略或用户审核。
- 标准中所有 `example.org`、`example.com`、`wutong.example` 域名均是**保留的示例占位符**，不是实际运营端点。后续发布时 MUST 替换 Schema 正式地址并冻结 Registry。

## 1. 不可退让的体系约束

1. **OFFLINE-001**：Writer、Knowledge、Publisher MUST 能在没有 Network 后台、Server、账户、网络、Agent Runtime 时完成各自**本地**核心功能；用户已有可用的编译器/字库依赖除外。
2. **FILES-001**：Standalone 模式 MUST 直接读写用户的原生文件；不得因为不创建 Space 或 Object 而拒绝打开或保存。
3. **FILES-002**：无修改保存 MUST 保持输入字节（含 BOM、行结束符、空格、原注释）不变；除非用户显式触发编码或格式化转换。
4. **AGENT-001**：Agent Principal MAY 在离线模式存在。Agent 的模型、运行时和远程 API 均不是 Core 的强制依赖。
5. **NET-001**：Network 的 Qt GUI 与用户可选 Rust 后台 `wutong-networkd` 属同一产品但可独立启停。CLI 和 Wutong Server 统一 Rust，不依赖 Qt。
6. **SEC-001**：拥有查看权限不蕴含提案、直接修改、签署、发布、删除、部署权限；未证明的主体或权限声明不能执行远端写入。
7. **INTEROP-001**：外部协议映射 MAY 有损，但 MUST 报告保真损失与目标限制，MUST 维护来源和远程映射，不得偷偷覆盖原生内容。
8. **PROTO-001**：不强制使用任何 Wutong 官方服务器或索引；协议规范、实现与服务提供方相互独立。

## 3. 协议功能 Profile 和兼容性

- **`WTP-Core`**：基本信封、标识、15 类当前 Registry 类型、结构验证、Revision/Relation/Task 不变量。
- **`WTP-Document`**：原生文件 Binding、字节哈希、结构 Anchor、关联和版本协调。
- **`WTP-Agent`**：Agent Principal/Manifest、Task、Proposal、Artifact 与 Provenance。
- **`WTP-Security`**：独立信任根、签名验证、Key Binding、Capability、重放与撤销策略。
- **`WTP-Sync`**：协作数据格式协商、状态交换、快照与恢复。
- **`WTP-Federation`**：解析、跨节点查询、订阅、签名发布和撤销请求。
- **`WTP-Service`**：知识服务模板、可执行 Query/Action、部署与权限隔离。
- **`WTP-Interop`**：外部 Protocol/Platform/Service 适配器及来源映射。

`implementation_id + implementation_version + supported_profiles[] + exact_feature_ids[] + limits` 是兼容性声明必需的概念。`WTP-Core` 测试通过不蕴含 `WTP-Security` 通过。

## 4. 核心数据与标识

### 4.1 标识种类

| 类型 | 表达 | MUST 保证 |
|---|---|---|
| `Principal/Space/Object/Revision/... ID` | `urn:uuid:<UUIDv7>`（RFC 9562） | 同一实体变更不更换标识；不与文件路径混同 |
| `Content Digest` | `sha256:<64 lowercase hex>` | 仅对原始内容的精确字节做 SHA-256 |
| `Protocol Envelope ID` | UUIDv7 | 重试保持不变；同 ID 不允许不同内容的无声覆盖 |
| `External Resource Ref` | 目标原生 URL、AT URI、Matrix ID 等 | 映射和源原始身份分开存储 |
| `Node Endpoint` | HTTPS URI + 经验证的服务描述 | URL 位置可变；URL 不等于可信身份 |

`sha256:` 在本 Profile 中是字段值语法而**不是已注册 URI scheme**。UUIDv7 时间戳不可作为可信序列号、事件因果或授权凭证。

### 4.2 对象与内容分离

一个 Object 有不可变的 `object_id`，可更新当前 Revision 引用。每个 Revision 有 `revision_id`、`parents[]`、`content_digest`、`author_id`，子版本可合并多个父版本。对象内部的标题/属性/关系具有各自元数据；相同内容哈希的两个 Object **不能自动合并为同一身份**。

`Relation` MUST 记录发起者，不能让远端目标自动认可引用者的声明。`Annotation` MUST 指定目标及定位方式；定位失败时报告 orphan/stale，不能猜测性附着到无关段落。`ExternalBinding` 只是已建立的外部映射，不自动表达平台账号所有权验证。

## 5. JSON 交换格式（候选冻结）

### 5.1 信封

```json
{
  "protocol": "wutong/0.1",
  "kind": "wutong.object",
  "id": "urn:uuid:019a1111-1111-7111-8111-000000000064",
  "occurred_at": "2026-10-18T10:00:00Z",
  "payload": {
    "object_id": "urn:uuid:019a1111-1111-7111-8111-000000000004",
    "space_id": "urn:uuid:019a1111-1111-7111-8111-000000000002",
    "owner_id": "urn:uuid:019a1111-1111-7111-8111-000000000003",
    "object_type": "document",
    "media_type": "text/markdown",
    "byte_length": 11,
    "content_digest": "sha256:5a02a91e919377ce67a4af9dedfd3c13be1639c00f6485552a77a611ae5e8b7c",
    "binding": {"kind": "file", "relative_path": "notes/demo.md"}
  }
}
```

上面摘要是**说明性字段**，不能据此断定示例长度与哈希对应；机器可核对的真实向量见包内 `vectors/`。

### 5.2 字符、值与严格解析

`WTP-Core-JSON-0.1` MUST 采用严格 UTF-8 JSON，MUST 拒绝重复 Object 成员、无效 UTF-8、非有限数、孤立代理项、过深嵌套、超出限制的消息。为消除跨语言 JCS 数字差异，**本候选约束型配置明确禁用 JSON 浮点数**，整数仅允许 `[-(2^53-1), +(2^53-1)]`；更高精度数值使用定义了语义的十进制字符串。**所有 JSON 成员名限制为可打印 ASCII**，业务内容的字符串值仍可以包含完整合法 Unicode（不可进行静默 NFC 归一化）。

这是对 RFC 8785 的**有意缩小的数据域**，不是宣称任意 JSON 文档都可由当前参考实现完整 JCS 化。ASCII 键按 Unicode 码点排序与 JCS 的 UTF-16 属性名排序一致，整数可用安全范围的相同数值表示。未来若开放 Unicode 成员名或浮点数，必须推出专用 JCS 全面互操作测试，不得静默改变本配置下的已签名字节。

- `occurred_at` 和 `issued_at` 在候选 Profile 中采用 UTC 秒精度 `YYYY-MM-DDTHH:MM:SSZ`，不能作为因果顺序依据。
- Schema 按 JSON Schema Draft 2020-12 校验；`format` 在部分验证器中仅作为注解，本规范所有安全相关日期必须做额外语义验证。
- 未经 Schema 及语义验证的 JSON 不能直接用作文件路径、系统命令、外部 URL、权限或 Agent 工具参数。
- `extensions` 和 payload `x` 只能有明确归属的命名空间键（如 `org.example.feature`），扩展不会改变 Core 所有权和认证语义。

### 5.3 身份映射与密钥不在核心消息字符串中完成

`principal_id` 仅是 UUIDv7 字符串；它自身**无法证明密钥所有权**。网络验证需要受信任的 `Principal ↔ Key Binding`，由受权主体签发并提供密钥生命周期。当前 schema 不包括完整 KeyBinding 链，属于 **Security 发布阻断项**；未完成前安全交换不能自称已符合 WTP-Security。

### 5.4 协议版本与变化

- 本工作包在尚未发布最终 v0.1 规范前沿用 `protocol = "wutong/0.1"`；先前的 `draft.1` 是**未冻结的实验草案**，在本版引入签名字段变更，**两者不保证互操作**。
- `rc.1` → `rc.2` 可以更改草案 Wire 格式，但 MUST 清楚发布差异及迁移工具；正式 `v0.1.0` 标记以后，同一主次版本的已声明必需字段不得作破坏性变更。
- 扩展 Profile 通过名称与语义版本协商，未知非关键扩展可转发，未知 **critical** 扩展 MUST 拒绝执行。

## 6. 规范化与签名（Security Candidate，不作生产安全承诺）

### 6.1 签名对象

签名消息增加：

```json
"auth": {
  "signer_id": "urn:uuid:019a1111-1111-7111-8111-000000000001",
  "key_id": "local-key-01",
  "issued_at": "2026-10-18T10:00:00Z",
  "nonce": "AAAAAAAAAAAAAAAAAAAAAAAA"
},
"proof": {
  "alg": "Ed25519",
  "sig": "<86 chars base64url without padding>"
}
```

**确切签名字节**：

```
Ed25519-Sign(private_key, ASCII("WUTONG-SIG-V0.1") || 0x00 || JCS(message_without_proof))
```

`auth` 字段受签名覆盖，`proof` 整个字段不参与 JCS；`proof.alg` 固定 `Ed25519`，签名为 64 字节，无填充 canonical Base64URL 编码。客户端必须先固定算法并进行完整验证，再按授权策略处理请求。禁止盲信消息内的公钥声明来决定 Principal 权限。

本实验实现提供 Python Ed25519 签名和 Node.js 独立验证、RFC 8032 固定向量及篡改反例。**但它还没有可靠的跨节点 Key Binding 注册、密钥轮换/历史验证/撤销、生产重放数据库，因此仍只达到 Security 实验验证，而非 Security 符合性声明。**

### 6.2 存档证明与实时请求的区别

- **存档签名（Artifact Proof）**：在历史时间签署的对象可离线验证签名的数学有效性，但必须另外建立当时密钥控制和来源可信度，不能要求 `issued_at` 永远在当前五分钟内。
- **实时写入/调用（Invocation）**：除签名外，必须使用时效、nonce 或 Idempotency-Key 和持久重放检测，防止已经执行过的请求被重复执行。
- 本包 `verify_envelope` 当前只实现 **五分钟时钟窗口的实时请求实验**，不应拿它当作长期历史签名验证器。
- 同一签名消息 ID 和不同字节视为可疑分叉（equivocation），节点 MUST 保留审计并阻止静默覆盖。

### 6.3 根授权与 Capability 链

Capability 必须至少指定 `issuer_id`、`audience_id`、`resource_ref`、`actions`、`not_before`、`expires_at`、`delegable` 和可选 `parent_id`。授权执行器 MUST：

1. 校验根控制权和每级签名。资源 Owner 声明不等于所有权证明。
2. 校验 Principal 与当前身份密钥、密钥状态及授权上下文的绑定。
3. 校验父授权的受众恰好是子授权的颁发者；子动作是父动作子集；子时效包含于父授权时效；父明确允许再委托。
4. 校验资源范围、拒绝未定义 wildcard/Glob/Regex 的模糊权限扩张。本候选权限参考实现只支持 **exact resource + exact action**。
5. 校验撤销与新鲜度；离线且无法获取敏感写入/公开发布所需的撤销状态时，按明确的离线策略 **拒绝或推迟**，不得默许。
6. 限制链深度、循环、授权引用大小和验证计算预算；默认拒绝未明确授权的行为。
7. 对执行侧本地文件路径、外部服务器资源和部署动作进行最终的资源策略判定。

当前测试验证了**在假定所有授权均已密码学验证、撤销信息已提供**前提下的委托语义，不能替代真实信任根或 UCAN 完整实现。

### 6.4 私有空间 E2EE

仅定义未来 Profile 的最低安全原则，不冻结加密套件：每个加密域与设备有独立密钥；成员移除需要密钥轮换；签名更新先认证后解密及 CRDT 合并；不得将个人私有 Blob 明文投递到公开 Federation。可以研究 MLS（RFC 9420）及 AnySync，但不能把 Signal/Matrix 的加密格式视为透明通用 E2EE Bridge。生产端到端加密必须经历形式化威胁建模、第三方评审与恢复场景测试。

## 7. 原生文档 Profile（Document）

### 7.1 文件绑定

- `DocumentBinding` MAY 完全不存在：任意 standalone 源文件仍应能编辑。
- 绑定存在时，对象 stable ID 与工作区相对路径独立；路径必须进行平台安全解析，禁止绝对路径、`..` 路径穿越、symlink/junction/reparse point 逃逸、挂载目录越界、DOS 设备名等。
- Object `content_digest` 对文件**精确字节**计算，不经过 Unicode 归一化、换行转换或 AST 再序列化；`byte_length` 是文件字节长度而非字符长度。
- 多格式预览使用语言专属 Parser，保存用 minimal source edit，未知扩展不能造成丢失。

### 7.2 写入协调器（必须实现）

单独写磁盘文件和 SQLite 表不具备共同的原子提交：`rename()` 原子性与 `fsync()` 持久性、SQLite 事务持久性是不同问题。建议采用：

```
validate(base_digest, authorization, file identity)
  → create staging + fsync(file) + fsync(directory)
  → SQLite WriteIntent(prepared) COMMIT
  → atomically replace within same volume, with concurrency guard
  → fsync(directory)
  → SQLite head Revision + intent(committed) COMMIT
  → recover/reconcile on restart
```

恢复规则：磁盘哈希=`new_digest` → 幂等完成 DB 提交；磁盘哈希=`old_digest` 且 staging 哈希=`new_digest` → 检查锁/条件后 roll forward；磁盘哈希非两者 → 标记**冲突**并保留文件，不自动覆盖。必须定期清理 orphan staging、维护意图日志并保证备份/恢复。

本包 Python PoC 验证以上逻辑的**无竞争故障点**；未实现 Windows NTFS、macOS APFS 和 Linux 文件元数据/权限完整性及跨进程 CAS，因此不得替代正式 `FileCoordinator`。

### 7.3 注释锚点

Annotation 应同时保存目标 Object、可选 Revision、TextQuote/位置或结构节点，允许在文档变化后重新锚定，但必须报告 `resolved` / `stale` / `orphan` 等状态。可映射 W3C Web Annotation 模型。不能把字节偏移与 Unicode 码点/UTF-16 位置混用。

## 8. Revision、Event 与因果一致性

- Revision DAG MUST 无环、父版本可追溯；引用暂缺时 MAY 暂存为 unresolved，不能将不完整历史谎称成验证通过。
- `parents[]` 的成员不重复；不同分支可以并行存在；自动合并的文本收敛不等于语法或语义正确。
- `occurred_at` 可以用来显示但不是全局可信顺序。Event `causes[]`/CRDT 时钟记录因果关系；Service 边界引入明确定义的顺序和并发冲突政策。
- 对同一 Event ID 收到字节不同的签名消息，节点必须隔离和记录，不能择优覆盖。
- 所有外部发布、Agent 操作、权限变更应形成可授权审计记录；审核状态与知识事实正确性互不替代。

## 9. Agent 原生 Profile

### 9.1 Agent 是主体，不是模型供应商

Agent 可以是本地进程、远程服务或代理执行体；可有独立 Principal、Space、Relations 和可选 Manifest。Agent Manifest 的能力列表只能用于发现/路由，不能被当作资源权限凭据。Agent 的工具与模型运行时必须可选。

### 9.2 Task 状态机

合法转换：

```
created → assigned | cancelled
assigned → accepted | cancelled
accepted → running | cancelled
running → awaiting_approval | completed | failed | cancelled
awaiting_approval → running | completed | failed | cancelled
completed | failed | cancelled → terminal
```

在某一 Task 上执行迁移，执行器 MUST 检查基础 Task 版本、身份授权、有效执行租约与幂等键；声明 `completed` 不意味着某个无法回滚的外部副作用已经撤销或必然发生。终态不能被任意逆转，重试应分配独立 attempt ID。

### 9.3 Proposal 与 Artifact

Agent 请求修改原生文件时，默认创建 `Proposal`，至少包含 `object_id`、`proposer_id`、`base_digest`、`proposed_digest`、`intent` 与审阅状态。`Proposal=accepted` 与 `Proposal=applied` 不同：后者必须在权限、基础版本和实际持久化写入都验证后才能记载。Artifact 用 `content_digest` 关联真实产物并验证精确字节。

### 9.4 不可信输入、来源与审核

网络文本、论坛消息、工具结果和来自其他 Agent 的消息都是**低信任数据**。禁止内容指令自动升级身份、授权或用户批准。每次敏感操作都经过本地授权执行器；Agent 创建知识不代表所产生的观点经过事实核验。

审计最小字段：`actor`、`delegator`、`task_id`、`input_revision[]`、`tool_id`、`output_artifact[]`、`reviewer`、`policy_decision`。来源可映射 W3C PROV；默认不得公开完整提示词、用户私密上下文、模型内部推理或 API 密钥。

## 10. 同步与非实时协作（实验 Profile）

### 10.1 模式区分

| 模式 | 持久化权威 | 关键机制 |
|---|---|---|
| Solo | 内存 DocumentSession + 原生文件协调器 | 修改/保存、外部变更检测 |
| Live | 持久化 CRDT 状态与活跃会话 | Presence 独立通道、增量更新 |
| Offline | 已持久化变更 DAG/CRDT | 重连、重传、快照、幂等 |
| Review | 受权版本与 Proposal/ChangeSet | 人工/策略审核、三方合并 |

**Sync Profile 不等于 Core**。不参与任何协作的用户不需创建同步状态。协作源文本原则上同步**原始文本**，各语言 Parser 分别处理预览；不把 Markdown AST 当成所有语言的共享数据格式。

### 10.2 传输无关握手草案

`HELLO{protocol,profiles,algorithms,space_ref,max_frame}` → `AUTH{challenge,response,capabilities}` → `SYNC_OFFER{heads,snapshot_ids,codec}` → `SYNC_REQUEST{want,...}` → `SYNC_CHUNK{digest,bytes}` → `SYNC_ACK{digest,frontier}`；Presence 单独传输，不必须持久化。此结构属于 **WTP-Sync 实验设计**，并非现有生产可交换 Wire Schema。

不得将 Automerge 消息误当成 Yrs 消息；不同 CRDT 需要通过 `codec ID + version` 明确协商。没有共同编解码器的客户端应退回快照/Review 流程而非声称自动收敛。历史压缩必须考虑长期离线客户端所需前沿。

## 11. Federation（实验 Profile）

### 11.1 可组合角色

`Client Node`、`Sync Node`、`Service Host`、`Federation Node`、`Indexer/AppView`、`Agent Worker` 是可以组合部署的节点角色。不存在强制中央服务器；公开服务持续可用必须有在线副本或网关，纯 P2P 不保证 NAT 穿透与全天候在线。

### 11.2 资源发现与 API 草案

在域名自有且管理员主动配置的服务上，候选入口为 `GET /_wutong/v0.1/meta`（避免在未完成 IANA/社区注册前宣称 `/.well-known/wutong` 为正式标准）；其他候选 API：

| Method | Path | 语义（尚未冻结） |
|---|---|---|
| GET | `/_wutong/v0.1/meta` | 功能 Profile/Schema/端点信息 |
| GET | `/_wutong/v0.1/objects/{id}` | 获取公开或经授权对象 |
| GET | `/_wutong/v0.1/revisions/{id}` | 获取特定不可变版本 |
| POST | `/_wutong/v0.1/resolve` | 解析外部及跨节点资源 |
| POST | `/_wutong/v0.1/subscriptions` | 授权订阅资源变更 |
| POST | `/_wutong/v0.1/invocations` | 发送签名、可重放检查的动作请求 |

这些 **只是 API 设计约束**，还没有统一状态码、认证错误、分页/游标、Rate Limit 和真实双节点实现，不能标记为生产 Endpoint 标准。必须提供 HTTPS/TLS、禁止 SSRF 的目标地址验证、解析/重定向限制与独立授权。

### 11.3 一致性与删除语义

联邦通知一般是最终一致而不是同步事务。`Delete/Withdraw` 表示撤销本节点展示/请求远端删除，不能保证外部缓存和副本已被物理清除。已公开发布信息可能被复制，用户 UI 不能夸大隐私回收保证。

## 12. Service 与 Builder（实验 Profile）

Builder 的 Service 定义至少包含 `Sources`、`Types`、`Queries`、`Views`、`Actions`、`Policies`、`Runtime`、`Distribution`；Service Profile 需要把只读静态站与有持续业务状态的论坛、问答、媒体和 IM 明确区分。

- Service Spec 是可以迁移、版本化的对象，但不允许在公开 Spec 中嵌入 Token/私钥。
- 由 Wutong Server/选定服务节点执行 Service Runtime；Publisher 负责文档编译，Builder 负责服务生命周期，不能混淆。
- 对外服务节点必须只获取 Publication Materialization（经明确公开的字段/媒体），不能默认解密全部私有 Space。
- `Action` 需资源政策、调用者身份、幂等、速率限制、审计和隔离执行；外部 Agent 不能通过 Service Spec 自行扩大权限。
- 媒体服务应考虑 HTTP Range、转码、版权/授权、Cache-Control；IM Bridge 必须标记 E2EE 信任边界。

## 13. Interoperability：能力而不是虚假的“全能双向同步”

### 13.1 适配层

```
Wutong Knowledge Object / Event
            |
    Semantic Representation (Article / Thread / Answer / Track / Message)
            |
      Projection & Sync Policy
            |
   Protocol Adapter → AT Protocol, ActivityPub, Matrix, MCP, A2A ...
   Platform Adapter → WordPress, Halo, Mastodon, Misskey, Telegram, ...
   Service Adapter  → Blog/Forum/Q&A/Media/IM Business Model
```

Adapter 必须声明动态能力：`read/create/update/delete/reply/react/upload/subscribe/draft/schedule/webhook/identity` 和 `fidelity`、作用范围、账号授权、速率及文件大小限制。理论上支持 ≠ 当前账号有权操作；不提供稳定 API 的平台只能声明人工辅助/导出能力。

### 13.2 ExternalBinding 和环路控制

每个外部投射保存 `object_id + adapter_id + account_ref + remote_ref + source_revision + sync_policy + target_capabilities + transform_loss_report`。远端回流 MUST 去重并区分：来源正文本身 / 评论 / 审核建议 / 新对象。不可把 Mastodon 回复直接追加进原始 `.md`，也不可反复执行 `WTP → WordPress → RSS → WTP` 造成发布循环。

### 13.3 对外协议的恰当边界

- ActivityPub：关注、动态、评论、Announce 等；不是逐字符 CRDT。
- AT Protocol：公开记录、身份及 AppView；不是私有 E2EE Workspace 的默认存储。
- Matrix：实时房间与消息；不是任意知识图谱的替代品。
- MCP：工具与资源访问；A2A：跨 Agent 任务协作。两者由 Gateway 对接 WTP 的 Agent/Capability/Task 而非成为 WTP 身份授权真相。
- WordPress/Halo/Hugo/Hexo/知乎/微信公众号等：根据授权与平台限制按需发布/回读，不能承诺所有平台原生双向写入。

## 14. 跨语言 SDK 与 C++/Rust 边界

| SDK | 首选实现 | 本地嵌入路径 |
|---|---|---|
| Rust | `wtp-core` Rust 2024 原生模型 + async client | 原生本地 Core |
| C++ | C++23 Schema Model + HTTP/IPC client | 直接链接 C++ Core；必要时 C ABI |
| C# | idiomatic async .NET client | 按需 P/Invoke，不能强制 |
| Python | async/sync Python client | 按需 pyo3/native wheels；不强制 |
| Go | context-aware Go client | 独立实现 Wire/HTTP；避免强制 cgo |
| TypeScript | 浏览器/Node/Web client | 浏览器 IndexedDB/Service Worker 可选 |

所有 SDK MUST 通过相同的静态合同样例与协议版本协商测试，但 SDK 对象模型不必与 Wire JSON 一一同构。不得假设 Rust FFI 自动解决跨语言数据模型或所有权问题。`AGPL-3.0-only` 对 SDK 静态/动态链接及分发存在法律义务，需要第三方评估；纯协议的独立重实现没有自动变成原仓库衍生代码。

## 15. 默认错误与拒绝语义

建议使用结构化错误代码，并明确边界：

| 错误代码 | 情景 | 处理原则 |
|---|---|---|
| `ERR_SCHEMA` | 缺字段/格式错误/未知 critical 扩展 | 拒绝解析或执行 |
| `ERR_VERSION` | 不支持的 Profile/协议版本 | 声明支持项、拒绝破坏性协商 |
| `ERR_SIGNATURE` | 签名失效/密钥不可验证 | 拒绝授权动作 |
| `ERR_PERMISSION` | 动作超出 Capability/ACL | 拒绝并记录最小审计 |
| `ERR_REPLAY` | 已处理的 nonce/idempotency key | 根据幂等策略返回旧结果或拒绝 |
| `ERR_CONFLICT` | 原始文件或对象基础版本变化 | 保留内容、进入 Review |
| `ERR_UNRESOLVED` | 对象/版本/关系目标不可访问 | 标记不完整，不假称已验证 |
| `ERR_RATE_LIMIT` | 请求超出资源配额 | 提供安全的重试/退避信息 |
| `ERR_UNSUPPORTED` | 平台或实例无对应能力 | 能力降级，不伪造成功 |

这些错误代码仍是规范草案，HTTP/gRPC/SDK 错误映射应在各 Profile 正式版定稿。

## 16. 安全威胁模型（基础）

| 攻击面 | 对手能力 | 预防/检测措施 |
|---|---|---|
| Signed Event | 篡改、重放、算法混淆 | JCS、Ed25519、密钥验证、nonce/时效与持久防重放 |
| Capability | 提交伪造委托或扩大权限 | 根所有权、链验证、动作/范围衰减、撤销与执行侧检查 |
| File Binding | 路径穿越、symlink 替换、外部修改 | dirfd/安全路径解析、OS 锁、写入意图、冲突备份 |
| Federation | SSRF、DNS Rebinding、伪造重定向 | 出站目标地址策略、TLS 校验、IP/端口限制 |
| Agent | Prompt Injection、工具输出混淆 | 外部内容=数据；独立政策层；高风险动作审批 |
| Adapter | 凭证泄露、恶意插件、API 误用 | 独立进程、最小权限、密钥隔离、审计与限流 |
| E2EE | 成员撤销、离线旧钥、转发桥接 | 加密域/密钥轮换/明确桥接信任边界 |
| Service | RCE、XSS、CSRF、恶意媒体 | 沙箱、内容消毒、配额、成熟转码器及补丁管理 |
| Availability | 反复重连、大消息、解析炸弹 | 消息/结构/带宽/计算预算和回压 |

## 17. 版本、扩展与注册表治理

- 建立机器可读 Registry，分别登记 `kind`、`action`、`predicate`、`profile`、`error`、`codec`、`extension namespace`。
- 项目内 `wutong.*` 名称由项目治理维护；第三方自有域名反向命名空间，避免未授权冒名。
- 标准变更通过公开 WIP（Wutong Improvement Proposal）、兼容性评审与公开测试向量；不在既有稳定 Profile 中改变签名字节、权限意义或 ID 解释。
- Registry 锁定与 Schema 公开 URI、贡献流程、变更记录、安全披露窗口应当在正式 tag 前完成。
- 一项 Profile 被标记 Deprecated 不得破坏现存原生文档访问；需要过渡期限及导入/导出策略。

## 附录 B：发布判定

**目前可以公开的是 Wutong Protocol v0.1 的“征求意见版规范、Schema、测试样例和实验参考实现”。** 这已经显著优于仅讨论数据结构的概念草案，但仍**不能**正式声明：可信跨节点身份安全已解决、Agent 委托已生产化、CRDT 多端互通已证明、联邦功能可上线，或所有产品符合 WTP v0.1。真正的协议正式发布应遵循 §18 的全部门禁，尤其是至少两个独立实现对必需功能的互操作、跨平台故障测试和安全评审。
